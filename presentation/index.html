  • The workload has a few stable process roles and no Kubernetes-specific requirement.

04 · Runtime design

How does the final architecture work?

PublicApplicationDataDelivery / Ops
Public surface: only the ALB. Compute and data: private. AWS API access: VPC endpoints. State: managed outside containers.

What to say

  • The request path is intentionally simple: user, public ALB, private web task, then PostgreSQL and Redis.
  • The ALB and subnet topology span two Availability Zones; the web service has a desired count of two.
  • Worker and scheduler use the same application image with different commands.
  • RDS and Redis are managed services because persistent data has a different lifecycle from stateless containers.
  • Private tasks reach ECR, S3, Logs and Secrets Manager through VPC endpoints; no permanent NAT Gateway is required in the baseline.
  • The baseline therefore has no general public Internet egress; arbitrary webhooks or UptimeRobot synchronization need an added egress path.

Transition

The architecture is only one part of the story; the working method explains how I reached it safely.

Likely questions

Is the data tier multi-AZ? No. The demo RDS instance and Redis node are single-AZ. The ALB spans two AZs; the web service has two tasks and subnets in both AZs, but the retained evidence does not prove one task per AZ.

What to say

  • Terraform makes the architecture declarative, reviewable and repeatable.
  • The state is stored in an encrypted, versioned S3 backend with lockfiles.

What to say

  • Pull requests run the complete validation and separate security workflows.
  • Production images are tagged sha-<commit>; I do not rely on mutable latest.
  • A private one-off migration must succeed for that exact SHA before deployment is allowed.
  • An explicit deployment dispatch then reaches the GitHub Environment operator-approval boundary; the rehearsal does not claim independent four-eyes review.
  • The rollout stabilizes web first, then worker and scheduler, verifies health, and attempts rollback. Initial service bootstrap is a separate operator/Terraform phase; the Environment protects later releases.

Transition

Likely question

Does every push deploy? No. Image publication and runtime deployment are separate. Deployment requires workflow dispatch, exact migration evidence and production approval; PRODUCTION_ENABLED=false pauses the path after teardown.

Not just “RDS says available.”

A private Fargate task connects to the restored database and checks that the expected application data is actually present.

What to say

  • Enabling automated backups is configuration; it is not proof of recovery.
  • The rehearsal writes a unique probe, takes a snapshot and restores a disposable private RDS instance.
  • A one-off Fargate task checks both the exact probe and Django migration history.
  • The script verifies temporary DB and snapshot absence and requests task-definition cleanup; the rehearsal read-back found no active restore task definitions.
  • This proves that the backup contained usable application state.

Transition

After proving recovery, I also checked that re-running the infrastructure definition would not create drift.

Likely question

Does this prove every disaster scenario? No. It proves the documented snapshot-restore path and semantic data checks. It does not claim cross-region disaster recovery.

  • Idempotent infrastructure is different from an immutable application release.

Transition

With creation, delivery, recovery and convergence tested, the final question is simple: did the complete system work?

Likely question

Why does Terraform ignore task-definition drift? Because release automation owns post-bootstrap application revisions. Terraform still owns service structure, networking, counts and destruction, so a later apply cannot roll back a newer release.

Questions?

What to say

  • The main lesson was a structured way of working, not simply learning AWS service names.
  • Understand behavior, add one layer at a time, and validate every boundary.
  • Choose technology according to the workload, not popularity.
  • Separate infrastructure, releases, credentials and state so changes have clear owners.
  • Treat recovery and destructive operations as designed, testable paths.

APPENDIX D

OIDC and release controls

1Fail-closed configuration

Exact repository, main branch, account, region, resource names and required variables.

2Publisher identity

Job-level OIDC permission; restricted role publishes immutable ECR images.

3Migration evidence

MIGRATION_EVIDENCE_SHA must equal the workflow SHA before deploy.

4Approval boundary

GitHub Environment approval is a separate job without AWS credentials.

5Deployer identity

A separate branch-bound OIDC role registers task definitions and updates ECS services.

6Post-deploy verification

Web stabilizes first; all services stabilize; public health endpoint must pass.

The production path is opt-in. After teardown, PRODUCTION_ENABLED=false pauses publication and deployment.

Jury support

  • The approval job is intentionally separate from the deployer job.
  • The deployer token remains compatible with the branch-bound OIDC trust.
  • No long-lived AWS access keys are required in GitHub.
