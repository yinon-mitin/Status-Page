Architecture Reference

Status-Page — System Architecture

Self-hosted service status & incident communication platform. A monolithic Django application serving a public status page and an operator dashboard, backed by PostgreSQL for state, Redis for caching and a job queue, and RQ workers for all asynchronous and scheduled work.

Django 4.1.4 Python ≥ 3.10 PostgreSQL ≥ 10 Redis ≥ 4.0 Gunicorn + NGINX django-rq / rq-scheduler DRF 3.14 + drf-yasg Tailwind + Alpine + htmx Pattern modular monolith

01 Runtime topology

Three processes make up the application tier, all on the same host and all sharing one PostgreSQL database and one Redis instance. NGINX terminates TLS, serves collected static assets directly from disk, and reverse-proxies everything else to Gunicorn on 127.0.0.1:8001. No component of the system is horizontally partitioned — scale-out means running more Gunicorn workers or more RQ workers against the same backing services.

Request lifecycle

  1. NGINXTerminates TLS. /static/ is an alias to /opt/status-page/statuspage/static/ and never reaches Django. Everything else is proxied with X-Forwarded-Proto, honoured by SECURE_PROXY_SSL_HEADER.
  2. Gunicorn workerHands the WSGI request to statuspage.wsgi. Each worker holds a persistent Postgres connection for up to 300 s.
  3. Middleware chainsecurity → session → common → CSRF → auth → OTPMiddleware → messages → clickjacking → browser-reload → APIVersionMiddleware → ObjectChangeMiddleware → DynamicConfigMiddleware.
  4. DynamicConfigMiddlewareLoads the active ConfigRevision from the Redis cache (key config) into a thread-local, so runtime settings such as SITE_TITLE or MAINTENANCE_MODE resolve without a DB hit.
  5. View + ORMQuerysets are wrapped by RestrictedQuerySet.restrict(), which folds the caller's ObjectPermission constraints into the SQL WHERE clause.
  6. ResponseTemplate render (Tailwind-styled) or DRF serialization. ObjectChangeMiddleware commits the accumulated change-log rows in the same transaction and clears cached config on ConfigRevision writes.

02 Frontend layer

There is no SPA and no separate frontend service. The frontend is server-rendered Django templates styled with Tailwind, enhanced with Alpine.js for local component state and htmx for partial updates (tables, pagination, delete confirmations). Assets are compiled ahead of time with esbuild and committed to project-static/dist/, then collected into STATIC_ROOT and served by NGINX.

Two distinct surfaces

  • /api/docs/, /api/redoc/ open schema browsers
Operator — authenticated

03 Backend layer

A modular monolith. Domain logic is split into Django apps that each contribute models, forms, tables, filtersets, HTML views and a DRF API module in a repeating structure inherited from NetBox. Two optional plugins are loaded through a validated plugin framework rather than being hard-wired.

Plugin loading contract

For each entry in PLUGINS, settings.py imports the module, requires a PluginConfig named config, calls validate(PLUGINS_CONFIG[name], VERSION) to enforce min/max app version plus required_settings and default_settings, then appends the app to INSTALLED_APPS, extends MIDDLEWARE, and registers additional RQ queues named <plugin>.<queue>. Plugin URLs mount under /plugins/ and /api/plugins/; plugin cron schedules are registered by extras/plugins/__init__.py::register_schedules().

REST API surface

04 Data layer & entity model

PostgreSQL is the single system of record — there is no second database, no read replica in the shipped configuration, and no ORM sharding. Every persisted model inherits ChangeLoggedModel, which adds created/last_updated, snapshotting and an audit row, and swaps in RestrictedQuerySet so object-level permissions are enforced at the queryset level.

Redis — two logical databases

SectionDefault DBClientPurposeFailure impact
REDIS['tasks']0 django-rq / rq Job broker for queues high, default, low, plus the rq-scheduler sorted set. RQ_DEFAULT_TIMEOUT 300. No mail sent, no maintenance automation, no plugin polling. Web UI stays up.
REDIS['caching']1 django_redis Django cache backend. Holds config / config_version for the dynamic-config layer and cached view fragments. Requests fail or degrade — DynamicConfigMiddleware depends on it on every request.

Both sections independently support Redis Sentinel (SENTINELS, SENTINEL_SERVICE) and TLS, in which case the cache switches to SentinelClient + SentinelConnectionFactory.

Dynamic configuration

A second configuration plane sits above configuration.py: ConfigRevision rows edited in Django admin, activated into the Redis cache and read per-request into a thread-local by DynamicConfigMiddleware. Parameters include SITE_TITLE, SITE_SUBSCRIBERS, custom header/footer/CSS, ALLOWED_URL_SCHEMES, PAGINATE_COUNT, MAX_PAGE_SIZE, DEFAULT_USER_PREFERENCES, MAINTENANCE_MODE and CHANGELOG_RETENTION — changeable without a restart.

05 Asynchronous & scheduled work

All work that must not block a request — outbound e-mail, third-party polling, retention pruning and maintenance-window automation — runs on RQ. In practice only the default queue receives core work; high and low exist for plugins and future use.

Scheduled jobs

JobCronOwnerWhat it does
maintenance_automation* * * * *queuingStarts maintenances past scheduled_at (creates a MaintenanceUpdate, flips components to maintenance); completes those past end_at and restores components to operational

sync_uptimerobot_data* * * * *sp_uptimerobotPolls the UptimeRobot API, maps monitor status onto components, honours maintenance windows, writes MetricPoints, removes stale monitors

Cron registration is idempotent: QueuingConfig.ready() lists the scheduler's existing job function names and only registers what is missing (and skips entirely during manage.py collectstatic). Plugin schedules are declared in each plugin's queuing.py::schedules list. Operators inspect queues at /admin/background-tasks/.

07 Security & identity

Authentication
Sessions + TOTP
  • Stock django.contrib.auth.User; single custom backend ObjectPermissionBackend
  • django-otp with TOTP, static backup codes and YubiKey device support
  • Login view issues an OTP challenge (otp-device / otp-token); Django admin uses OTPAdminAuthenticationForm
  • QR enrolment rendered locally with segno — no external QR service
API credentials
Scoped tokens
  • 40-char hex key, optional expires, write_enabled flag blocking unsafe methods
  • allowed_ips CIDR allowlist checked against the client IP resolved from forwarded headers
  • last_used written at most once per minute; skipped in MAINTENANCE_MODE
  • TokenPermissions maps GET/HEAD onto the model's view_* permission
Authorization
Object-level permissions
  • ObjectPermission binds users/groups + content types + actions + a JSON constraints filter
  • Constraints are compiled to ORM filters and applied by RestrictedQuerySet.restrict() — enforcement is at the queryset, not the template
  • Views gate through ObjectPermissionRequiredMixin; EXEMPT_VIEW_PERMISSIONS is force-emptied
Auditability
Change log
  • ObjectChangeMiddleware + extras/signals.py record pre/post JSON snapshots per write
  • Correlated by request_id, attributed to the user, exposed per-object at <pk>/changelog/ and read-only at /api/extras/object-changes/
  • Retention enforced nightly by the housekeeping job
Transport
Edge hardening
  • TLS at NGINX with HTTP→HTTPS redirect; SECURE_PROXY_SSL_HEADER + USE_X_FORWARDED_HOST
  • X_FRAME_OPTIONS = SAMEORIGIN, CSRF middleware, ALLOWED_HOSTS mandatory
  • Upload ceiling client_max_body_size 25m
Public surface
Unauthenticated paths
  • Status page, subscribe/verify/manage/unsubscribe (UUID management key is the only secret)
  • /api/docs/, /api/redoc/, /api/swagger.json — permission_classes=()
  • /api/users/tokens/provision/ — username+password exchanged for a token, no prior auth

09 Architectural notes

Observations worth carrying into a design review
  • Notification fan-out is synchronous inside save(). Incident, IncidentUpdate, Maintenance and MaintenanceUpdate loop over subscribers and enqueue one RQ job each while the request thread is still open, all wrapped in a bare try/except: pass. A large subscriber list lengthens the write request, and any failure is swallowed silently.
  • Cache is on the critical path. DynamicConfigMiddleware reads the active config from Redis DB 1 on every request, so a cache outage degrades the whole application rather than just cold-starting it.
  • Maintenance subscriptions reuse the incident flag. Maintenance.save() and MaintenanceUpdate.save() filter subscribers on incident_subscriptions=True; there is no separate maintenance opt-in.
  • Component-scoped targeting is partial. Only components/signals.py honours component_subscriptions; incident and maintenance notifications ignore it and go to every subscriber with the incident flag set.
  • No webhook / push integration. Chat and paging integrations require the REST API or a plugin.
  • Single-host assumptions. MEDIA_ROOT is local disk served by Django, and plugin sync jobs are unguarded against concurrent execution — running two RQ workers on the same minute-cron sync is not idempotent by design.
  • Typo in a public route: subscribers/reqeust-management-key (statuspage/urls.py:34) — changing it is a breaking URL change for anyone who bookmarked it.
