Target AWS architecture — source runtime preserved

One application, three runtime roles

The supplied Status-Page source is a Django modular monolith. Its AWS design does not replace that model: it gives each required runtime process a managed container role and moves stateful dependencies to managed services.

Current applicationDjango, Gunicorn, NGINX, PostgreSQL, Redis, RQ Worker and Scheduler.
AWS targetECS Fargate, RDS, ElastiCache, ALB, ACM, ECR, Secrets Manager and CloudWatch.
Key guardrailRun two web tasks across two AZs; keep worker and scheduler singular because the source has media and concurrency limits.

Components and responsibilities

Hover a component to highlight its role in the target deployment.

⬡

Docker + ECR

Build once; store an image tagged with the Git commit SHA; reuse it for web, worker, and scheduler commands.

▣

ECS Fargate

Runs isolated containers without operating EC2 hosts. The web service is reachable through ALB; worker and scheduler are internal.

◈

ALB + ACM

The only public entry point. Redirects HTTP, terminates HTTPS, runs health checks, and uses an ACM certificate.

▤

RDS PostgreSQL

Private RDS with no public endpoint. Port 5432 is allowed only from the ECS security group; backups are retained for two days.

▱

ElastiCache Redis

Managed Redis. DB 0 is the RQ broker; DB 1 is the Django cache, matching the source configuration.

▣

Secrets + IAM

Runtime secrets stay in Secrets Manager. IAM grants short-lived, least-privilege access to ECS and CI/CD.

⌘

Terraform

Defines the VPC, subnets, security groups, services, data tier, logging, and outputs in version control.

↗

GitHub Actions

Tests code, builds and publishes the image, validates Terraform, then deploys a reviewed task definition.

◌

CloudWatch

Collects task logs and service metrics; alerts on failures, unhealthy targets, and data-tier pressure.

Clear boundary between facts and decisions

Source-derived facts

The supplied application uses NGINX → Gunicorn/Django, PostgreSQL, Redis DB 0 for queues, Redis DB 1 for cache, and separate `rqworker` and `rqscheduler` processes. Static assets and `MEDIA_ROOT` are local-disk assumptions.

Target AWS decisions

Cloudflare DNS-only maps status.yifilter.uk to a public ALB in two public subnets. ECS stays internal, with two web tasks across two AZs. RDS and ElastiCache are private.

Security model

Only the ALB is public: Internet → ALB SG → ECS SG → private RDS/Redis SG. VPC endpoints provide required AWS-service egress without NAT.

Public edgeCloudflare DNS-only directs status.yifilter.uk to ALB. ALB accepts 80/443 in two public subnets; ACM terminates HTTPS.
Private computeTwo web tasks run across internal application subnets. Only ALB SG can contact web on port 80.
Controlled dataPrivate RDS 5432 and Redis 6379 accept application traffic only from ECS SG. RDS backups are retained for two days.
Identity and secretsIAM and OIDC issue short-lived permissions; Secrets Manager stores credentials outside Git.

CI/CD delivery path

Two workflows keep application delivery and infrastructure changes reviewable but connected.

Application workflow

Test → Docker build → container smoke test → GitHub OIDC → ECR SHA image → render ECS task definition → rolling deployment → ALB health verification.

Infrastructure workflow

Terraform format and validation → plan artifact → review/approval → protected production apply → remote state and locking.

Implementation roadmap

The Wednesday local Docker milestone is complete. The next delivery is GitHub Actions → ECR, followed by Terraform foundation and ECS.
